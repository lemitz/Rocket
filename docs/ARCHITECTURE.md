# Архитектура и потоки данных (фактическое состояние)

См. [HANDOFF](HANDOFF.md) для требований и дерева файлов, [PROTOCOL](PROTOCOL.md) для байтового формата. Код — главный источник истины при расхождении с текстом.

## Узлы, роли и состояние

```text
  Windows PC #1/#2                                     Android phone #1/#2
  rocket.exe (Go)                                       Rocket Activity (Kotlin)
  ├── TCP listener 0.0.0.0:42070   ◀──── TCP ────────────┤ Socket client
  ├── UDP responder :42069        ◀── UDP broadcast ─────┤ PC discovery
  ├── Windows Downloads/<выбранная папка>               ├── MediaStore Download / выбранное SAF-дерево
  ├── private .rocket-staging/*.part                     ├── Share/Picker URI → ПОЕХАЛИ
  ├── RAM outbox: device_id → выбранные пути             ├── foreground poll → offer-get → offer-done
  └── native window: choose files/phone/Launch          └── Canvas rocket, progress, settings
```

ПК никогда не инициирует TCP-соединение с телефоном. В направлении ПК→телефон кнопка в окне ПК добавляет **предложения**, а открытый на телефоне Rocket сам опрашивает выбранный ПК и запрашивает эти файлы. Это не фоновые уведомления и не P2P: если экран телефона погашен/Activity остановлена, предложения ждут, затем истекают. Приложение не стартует FGS, WorkManager и службы; поддержка фона потребует отдельного решения пользователя.

Публичный ID ПК создан при первом запуске и хранится в `%APPDATA%\Rocket\config.json` рядом с `download_dir`; телефон хранит свой ID, выбранный ПК и URI дерева в `SharedPreferences`. ID нужны для выбора/маршрутизации и сверки *случайной* смены IP, **не для авторизации**. При выборе ПК телефон сравнивает UDP ID с ответом TCP `ping`; во время poll повторяет проверку ожидаемого ID.

## Телефон → ПК (PUT)

1. `MainActivity` принимает Share URI или выбирает файлы в Android DocumentsUI. На отдельном потоке читает `DISPLAY_NAME` и `SIZE`; выбранные файлы показываются на экране, но **не отправляются автоматически**. Share-грант временный; URI может стать недоступным.
2. По «Поехали» Rocket использует запомненный ПК (или предлагает выбрать) и проверяет `ping`/ID. На одном соединении последовательно выполняет `put` для каждого файла. Android требует известный размер и не доверяет ему без проверки фактической длины потока.
3. ПК проверяет метаданные и создаёт случайный файл в `<папка приёма>/.rocket-staging/`, отвечает `ok` до потока. Получает ровно `size` байт, считает CRC32C, читает трейлер; после совпадения CRC выставляет mtime (если пришёл), делает `Sync` и `Close` и перемещает в папку приёма **без замены существующего**. Коллизии превращаются в `name (1).ext` и далее. Только потом отправляет конечный `ok`.
4. После конечного ACK Android помечает файл подтверждённым и обновляет прогресс; после всей пачки показывает финальную карточку. ПК агрегирует статистику по TCP-соединению и завершает её при закрытии соединения. После отмены/сбоя частичный файл ПК удаляется; опубликованные ранее файлы той же пачки не откатываются.

## ПК → телефон (offers)

1. ПК показывает в меню телефоны, которые вызывали `poll` за последние **12 секунд**. Пользователь выбирает 1–256 исходных обычных файлов (диалог `GetOpenFileNameW` или перетаскивание в окно). Единственный онлайн-телефон (или запомненный `last_phone`) выбирается сам, иначе адресат выбирается в листе «На …»; затем слайдер «Поехали!». `internal/outbox` revalidate путей, размера ≤1 ТиБ и имени, записывает **ссылки на исходный файл**, размер/mtime и случайные IDs в память без копирования файла. Недоступный телефон не выбирается. Заявленный лимит очереди — 256 файлов на телефон.
2. Пока Android Activity `resumed` и нет активной операции, он примерно раз в секунду подключается к выбранному ПК, делает `ping`, затем `poll` со своим ID. ПК возвращает до 32 предложений в порядке очереди. Если предложений больше, последующие покажутся после подтверждения первых. Предложения исчезают после подтверждения, по истечении **30 минут** или после закрытия демона; очередь не переживает рестарт ПК. При каждом `offer-get` ПК заново открывает исходный файл и проверяет, что размер и mtime по секундам не изменились; это **не снимок неизменного файла**.
3. Android для каждого предложения на том же соединении запрашивает `offer-get`, пишет байты через `DownloadStore`, сравнивает CRC32C, закрывает и публикует файл и лишь тогда отправляет `offer-done`. В системных Downloads используется `IS_PENDING=1→0`; в выбранной SAF-папке — временный документ с переименованием. Последний шаг `offer-done` убирает предложение из RAM-очереди. Если публикация удалась, а подтверждение потерялось, возможно повторное получение и имя с `(1)`.
4. На телефоне успех означает проверку и публикацию. ПК считает файл доставленным **только после `offer-done`**: байты и трейлер отправлены ещё не значит доставлены. Если соединение оборвалось между трейлером и `offer-done`, сеанс на ПК завершается ошибкой. Если телефон не подключился за 25 с после слайдера, очередь сбрасывается (`outbox.Drop`) и показывается ошибка.

## Хранилища и жизненный цикл

- Windows папка по умолчанию находится через `SHGetKnownFolderPath(FOLDERID_Downloads)`, без предположения `C:\Users\...`. Путь из настройки должен существовать и быть абсолютным. GUI сохраняет изменение для **новых** TCP-подключений; текущие заканчивают в старой папке. `rocket.exe daemon` — console-режим; пустые аргументы запускают GUI. При запуске и смене папки чистятся только `rocket-*.part` старше 24 часов внутри `.rocket-staging`; это не фоновый сборщик/не мгновенная уборка после потери питания.
- Windows публикация использует тот же том и `MoveFileExW` без `REPLACE_EXISTING`/`COPY_ALLOWED`. Атомарная видимость готового имени ≠ гарантированная стойкость именования после отключения питания. Сетевые имена санитизируются; пользовательские пути staged-файлов не выдаются в UI телефона.
- Android `MediaStore.Downloads` позволяет писать в стандартную Download без разрешения на все файлы. В произвольное дерево доступ выдаётся пользователем через SAF; провайдер может не поддержать rename/delete или дать другую семантику атомарности. Приложение не сохраняет серверный mtime у принятого файла. Share URI может не сообщить размер → передача пока отклоняется.
- `MainActivity.onPause` останавливает опрос, `onStop` закрывает активную передачу. Плохое соединение для пустого опроса не беспокоит пользователя; сбой активной передачи локализуется и выводится. Текущий cancel отменяет сокет, **но не отклоняет предложение**: оно может прийти снова — см. задачи в [OPEN_ISSUES](OPEN_ISSUES.md).

## UI, локализация и кадры (один экран)

Обе платформы рисуют одну сцену: фон с кэшированными звёздами и свечениями, спрайт ракеты из иконки пользователя (`tools/genassets`), состояния **idle → launching → flying → departing → result / fail** с одинаковыми таймингами (дрожь и подъём при старте, штрихи скорости вдоль оси носа, след частиц, выход ракеты за край за ~0,95 с, дым, карточка через ~0,9 с). Контролы главного экрана: кнопка «Выбрать файлы» (idle), плашка файлов, строка адресата и слайдер (после выбора), шестерёнка. Слайдер срабатывает при ≥85% хода, иначе возвращается пружиной. Остальное в настройках.

**Windows.** Собственное окно Win32 (PerMonitorV2 через манифест в EXE, тёмная рамка DWM, иконка из ресурсов, `WM_DROPFILES`). `internal/desktop/gfx.go` — CPU-растеризатор со сглаживанием в BGRA-буфер; текст — GDI в служебный DIB, результат кешируется как маска. Direct2D только загружает буфер в `ID2D1Bitmap` и показывает его `EndDraw` с `D2D1_PRESENT_OPTIONS_NONE` (vsync); индексы методов `ID2D1HwndRenderTarget` сверены с `d2d1.h` (CheckWindowState 57, Resize 58; старый код использовал 55 и 56, из-за чего ресайз не работал). Анимация идёт, только пока окно активно и есть движение, статичный экран не перерисовывается. Список телефонов опрашивается таймером раз в секунду (`WM_TIMER`). RU/EN по первому предпочитаемому языку интерфейса Windows.

**Android.** `LaunchView` рисует всё на Canvas (кадры через `postInvalidateOnAnimation()`, на API 35+ `setRequestedFrameRate(HIGH)`, `preferredRefreshRate` для режима 120 Гц; после анимации сбрасывается). Подсказка «Подключаюсь…» меняется на «Отправка/Получение N%», когда пошли первые байты. Отклик: вибрация на пороге слайдера, при старте, успехе и ошибке. Настройки — обычные вью (`SettingsPanel`). RU/EN через `res/values{,-ru}`. Экран зафиксирован в портрете.

Эти API не гарантируют 120 **показанных** кадров/с; измерений на железе нет.
## Безопасность и границы обещаний

Это приложение без TLS и без аутентификации по требованию пользователя; не публиковать в Интернет и не запускать в чужом Wi-Fi. Проверка частного IP и правило Windows Firewall `Private/LocalSubnet` ограничивают доступ, но не идентифицируют клиента. Другой участник доверенной LAN может притвориться заявленным ID телефона, попытаться получить адресованный ему offer или отправить `put` на ПК. CRC32C защищает только от случайной порчи. Не обещать «100% атомарность», точно-однократную доставку всей пачки или потолок скорости Wi-Fi 6 без замеров на целевых устройствах.
