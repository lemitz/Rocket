# Rocket wire protocol v1 — фактический контракт

Реализация: [`internal/wire/wire.go`](../internal/wire/wire.go), [`internal/server/`](../internal/server/), [`internal/outbox/`](../internal/outbox/), [`android/.../RocketProtocol.kt`](../android/app/src/main/java/dev/rocket/android/RocketProtocol.kt). Любое изменение формата требует синхронного изменения обеих платформ и тестов. TCP устанавливает **только телефон**, Windows слушает. Здесь нет HTTP, TLS, mDNS или попытки обойти NAT.

## Обнаружение ПК

- UDP запрос на порт **42069**: ASCII `ROCKET_DISCOVER_V1` (точное совпадение). Телефон шлёт broadcast на локальные интерфейсы; доступность зависит от Wi-Fi/AP/firewall.
- Ответ ПК: UTF-8 `ROCKET_HERE_V1|<node_id>|<hostname>`, где `node_id` — 32 строчных hex-символа, стабильная **публичная метка** ПК. Отдельно допускается старый однопольный ответ `ROCKET_HERE_V1` для Android-парсера; актуальный ПК отвечает расширенным.
- Android собирает ответы разных ПК и предлагает пользователю выбрать; сверяет ID с TCP `ping`. Успех сверки — **не аутентификация**, отправителя UDP можно подделать. После смены IP нужно заново выбрать ПК.

## TCP framing

По умолчанию IPv4 `:42070`. Каждое управляющее сообщение:

```text
4 байта: uint32 Big-Endian длина N    |    ровно N байтов объекта JSON в UTF-8
N ∈ [1, 65536]; нет завершающего перевода строки и второго JSON внутри одного фрейма
```

После некоторых фреймов идёт **сырой поток файла без чанковых заголовков**, длина строго `size` байт; после потока снова управляющий фрейм. Все клиентские запросы имеют `"v":1`. На одном TCP можно последовательно выполнить `ping`, несколько `put`, `put-text`, `poll`, несколько `offer-get`/`offer-done` и `text-done`. При ошибке потока нельзя пытаться распознавать новый JSON поверх непрочитанных байт — сессию закрывают. Сервер ограничивает размер файлов **1 ТиБ**; смещения/возобновление не поддерживаются (`offset` должен быть нулём).

Примеры показывают *существенные поля*: Go-сериализатор может добавлять `"size":0` или `"offers":null` в ответы, где они не используются. Для `poll` всегда выдаётся JSON-массив `offers`, в том числе `[]` при пустом списке. Для ошибки: `ok:false` и `error` (не показывать сырое серверное сообщение в локализованном Android UI).

### `ping`

```text
C → S  {"v":1,"cmd":"ping"}
S → C  {"ok":true,"name":"MY-PC","id":"<pc_node_id>"}
```

Имя — имя ПК, `id` — публичная метка из Windows-конфига.

### `put` (файлы выбираются на ТЕЛЕФОНЕ)

```text
C → S  {"v":1,"cmd":"put","name":"photo.jpg","size":1000,"mtime":1792700000}
S → C  {"ok":true}                         # ПК создал временный файл
C → S  [ровно 1000 сырых байтов]
C → S  {"hash":"<8 lowercase hex CRC32C>"} # JSON-трейлер с length-prefix
S → C  {"ok":true,"saved":"photo.jpg"}  # окончательное подтверждение публикации
```

При коллизии ПК может ответить `saved:"photo (1).jpg"`. Имя нормализует `internal/fsx`; размер должен быть известен до отправки. `mtime` — необязательные Unix-секунды, допустимые сервером 0..4102444800. Ошибка/обрыв удаляет свой `.part`; уже сохранённые файлы той же пачки не откатываются. CRC32C Castagnoli — не криптографический MAC.

### `poll` (телефон объявляет себя доступным и узнаёт предложения)

```text
C → S  {"v":1,"cmd":"poll","device":"<phone_id>","device_name":"Nothing Phone"}
S → C  {"ok":true,"offers":[]}
# либо
S → C  {"ok":true,"offers":[{"id":"<offer_id>","name":"movie.mkv","size":1234,"mtime":1792700000}],"texts":[{"id":"<text_id>","text":"Привет!"}]}
```

`phone_id` — 32 строчных hex-символа в `SharedPreferences`, **не секрет**. Телефон делает `ping` и `poll` примерно раз в секунду только пока Activity открыта. ПК отображает телефон доступным 12 секунд после последнего poll. GUI ПК создаёт предложения лишь после явного выбора **локальных** файлов, адресного телефона и Launch. Offer — случайный 16-байтный ID (32 hex), исходный файл не копируется; предложение хранится в RAM до `offer-done`, 30 минут или рестарта ПК. На poll возвращается максимум 32 предложения за ответ. Все предложения адресованы заявленному `device`, которое не аутентифицируется.

### `offer-get` + `offer-done` (файл с ПК забирает ТЕЛЕФОН)

```text
C → S  {"v":1,"cmd":"offer-get","device":"<phone_id>","id":"<offer_id>"}
S → C  {"ok":true,"size":1234,"mtime":1792700000}
S → C  [ровно 1234 сырых байта]
S → C  {"hash":"<8 lowercase hex CRC32C>"}
# Android сверяет CRC32C и публикует файл в Download / выбранном дереве
C → S  {"v":1,"cmd":"offer-done","device":"<phone_id>","id":"<offer_id>"}
S → C  {"ok":true}  # предложение убрано из RAM
```

ПК открывает только путь, помещённый в outbox для данного `device`, и сравнивает тип файла, размер и mtime с моментом постановки в очередь. Нет произвольного сетевого `GET` по имени. После неудачи *до* `offer-done` предложение остаётся, а при следующем poll возможен повтор. ПК считает файл доставленным и показывает успех **только после `offer-done`**; если соединение закрылось раньше, сеанс на ПК завершается ошибкой, хотя телефон мог успеть сохранить файл (подтверждение потеряно). Если Android успел сохранить файл, но ACK потерялся, повтор может получить суффикс `(1)` — протокол **не exactly-once**.

## Короткие текстовые сообщения и буфер обмена

Текст не является файлом: он передаётся внутри JSON-фрейма и **никогда не сохраняется на диск Rocket**. Размер текста — **1–8192 байт UTF-8**, строка должна быть корректной UTF-8, без `NUL` (`\u0000`); переводы строк и emoji допустимы. Это предел *байтов*, а не символов. Не отправлять текст из буфера автоматически без действия пользователя: на ПК Ctrl+V на главном экране лишь подготавливает его, отправка только после свайпа «Поехали»; на Android есть «Отправить текст» (можно набрать/вставить через системное поле ввода) или Share → текст. Получатель автоматически заменяет содержимое своего системного буфера; не сохраняет сообщение как файл. Android 13+ может показывать системное уведомление о копировании.

### Телефон → ПК: `put-text`

```text
C → S  {"v":1,"cmd":"put-text","text":"Привет!"}
# GUI ПК ставит текст в системный clipboard; только после успеха:
S → C  {"ok":true}
```

ПК без GUI (`rocket.exe daemon`) не предоставляет clipboard и отвечает ошибкой, а не ложно подтверждает. Основной экран ПК показывает результат только после фактического копирования. Команда не принимает произвольный путь, имя файла или «копировать чужой буфер».

### ПК → телефон: `texts` в `poll` и `text-done`

Окно ПК добавляет сообщение только адресованному онлайн-телефону в RAM-очередь, так же как адресные предложения файлов. `poll` возвращает исходный `offers` для файлов (пустой массив обязателен) и **необязательное** поле `texts`: массив `{id,text}`. Это оставляет старым APK возможность игнорировать неизвестное поле (текст ими не принимается). На каждый ответ максимум 32 текстовых сообщения; при превышении размера фрейма 64 КиБ сервер укорачивает список и отдаёт остальное в следующих poll. Очередь на телефон — не более 256 сообщений, срок хранения до 30 минут; сбрасывается при закрытии ПК, отмене исходящей очереди или таймауте GUI. IDs — случайные публичные метки, **не защита**.

```text
# Телефон опрашивает ПК, видит texts[{id,text}], копирует text в системный clipboard
C → S  {"v":1,"cmd":"text-done","device":"<phone_id>","id":"<text_id>"}
S → C  {"ok":true}    # удаление сообщения из очереди после копирования
```

Если копирование не удалось, Android не отправляет `text-done`; сообщение будет снова предложено при следующем poll. Если копирование прошло, а подтверждение потерялось, повтор может снова заменить буфер. Несколько сообщений копируются по очереди, в буфере остаётся последнее. При одновременных предложениях файла и текста телефон сначала копирует текст, затем получает файлы. Один TCP может нести оба типа, но для UI ПК статистика файлов и сообщений разделена. **Нет гарантии exactly-once или сохранения истории сообщений.**

## Удалённые команды, которые НЕ нужно возвращать

`list` (содержимое Downloads ПК) и произвольный `get(name)` **удалены из TCP dispatcher**. Они были ошибкой предыдущего UX: получатель не выбирает файл отправителя. `rocket.exe ping`/`put FILE` работают лишь как локальная CLI-диагностика ПК, не вводить их кнопками на основном экране. `stage` из начального черновика Zap здесь нет.

## Таймауты, пределы и ограничения безопасности

- Фрейм: 64 КиБ; пустой/слишком длинный/невалидный JSON отвергается. Запросы других версий/неизвестные команды отвергаются. Команды на обычной сессии: серверный deadline 2 минуты; на сырой передаче устанавливается абсолютный deadline 1 час. Android использует connect timeout ~3 с, отдельные ограничения чтения; **запись в медленный provider может длиться независимо**.
- `put` и исходные предложения ограничены 1 ТиБ/файл; outbox — ≤256 ожидающих файлов на телефон, исходный выбор ≤256 файлов. Несколько файлов передаются последовательно на одном TCP-соединении. В текущем горячем пути нет ring-pool, socket 4 MiB tuning или возобновления больших файлов — не писать обратное в требованиях.
- Нет TLS, пароля и настоящей проверки устройства. Сосед по LAN может подделать телефонный ID и запросить/убрать чужой offer **или текст**, отправить свой `put` или `put-text` ПК и заменить его буфер обмена. Разрешайте порты только на доверенной частной сети. Сетевые фильтры IP и firewall — не механизм идентификации. По решению пользователя **не добавлять аутентификацию по собственной инициативе**.
