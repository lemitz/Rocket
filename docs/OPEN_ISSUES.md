# Открытые вопросы и несовершенства

Этот файл отсутствовал, хотя на него ссылались остальные документы; здесь он собран заново по коду на 23 октября 2026. Документация описывает **текущее** поведение, здесь — то, что сделано не до конца. Исправленное убирай отсюда.

## Не проверено на железе

- Реальные **realme GT 6T** и **Nothing Phone (3a)**, два ПК и два телефона одновременно, Wi-Fi 6, поведение OEM при Share URI.
- **Реальные 120 показанных кадров/с.** Эмулятор API 36 даёт 60 Гц. Для Android нужен Perfetto FrameTimeline. На Windows тест `TestFrameCost` меряет только стоимость отрисовки кадра в памяти (1,4 мс при 440×780 и 5,1 мс при 880×1560 на машине разработки), а не показанные кадры.
- Масштаб Windows выше 100%, второй монитор с другим DPI (обработка `WM_DPICHANGED` написана, живьём не проверялась). Потеря устройства Direct2D (`D2DERR_RECREATE_TARGET`).
- Русский интерфейс на Android показан только в Windows-снимках; на эмуляторе проверялся английский.
- Долгие и большие файлы, нехватка места, обрыв сети посреди передачи, уход в фон: логика есть, ручного прогона нет.

## Поведение

1. **Отмена не отклоняет предложение.** Кнопка «Отмена» на телефоне закрывает сокет, но предложение ПК остаётся и может прийти снова. Отмены на стороне ПК нет совсем (закрытие окна обрывает всё).
2. **Нет «ровно один раз».** Если телефон сохранил файл, а `offer-done` потерялся, повтор создаст копию с `(1)`. На ПК такой сеанс покажет ошибку, хотя файл на телефоне есть.
3. **Исходный файл на ПК не снимок.** Перед отдачей проверяются размер и mtime (с точностью до секунды). Изменение файла во время передачи не обнаруживается.
4. **Пачка не откатывается.** Если упал второй файл из трёх, первый остаётся на месте получателя.
5. **Таймаут ожидания телефона 25 с** (после слайдера на ПК). Потом очередь сбрасывается и показывается ошибка.
6. Файлы с неизвестным размером Android-провайдера не отправляются.
7. SAF-папка не гарантирует атомарное переименование; mtime у принятых на Android файлов не сохраняется.
8. **ПК → телефон только при открытом экране телефона** (нет службы, FCM или фонового опроса).
9. Порт `-port` ломает совместимость с APK: 42070 и 42069 жёстко зашиты в Android, в UDP-поиске и в правилах брандмауэра.
10. Телефон обнаруживает ПК по UDP-broadcast; он не проходит через «гостевую» изоляцию клиентов Wi-Fi, тогда адрес приходится вводить вручную в настройках.

## Интерфейс

- Главный экран Android целиком нарисован на Canvas, поэтому **TalkBack** не видит кнопки и слайдер (только `contentDescription` сцены). Настройки сделаны обычными вью и доступны.
- Экран Android зафиксирован в портретной ориентации; ландшафтной раскладки нет. Окно ПК можно менять по размеру, но раскладка рассчитана на портрет (в широком окне колонка стоит по центру).
- Текст на ПК рисуется GDI в оттенках серого (без ClearType), на очень мелких размерах чуть мягче нативного.
- Перетаскивание файлов в окно ПК принимает только обычные файлы; папки пропускаются с подсказкой.
- Список телефонов на ПК обновляется раз в секунду по таймеру, телефон считается открытым 12 с после последнего опроса.
- Проверка брандмауэра запускает `netsh advfirewall firewall show rule`, исправление запускает `rocket.exe firewall install` с запросом UAC и не проверяет, что пользователь согласился, кроме повторной проверки через 1,5 с.

## Тесты и сборка

- Нет тестов Android (`src/test`, `androidTest`), только JVM-смоук разбора UDP-ответов.
- Нет автоматического сквозного теста GUI. Сквозная проверка выполнялась вручную на эмуляторе API 36 с настоящим `rocket.exe` (оба направления, SHA-256 совпал); как её повторить, написано в [BUILD_TEST.md](BUILD_TEST.md).
- `go test -race ./...` занимает около 40 с из-за теста отрисовки под детектором гонок.
- Проект теперь в Git (`main`), но `rocket.exe` и APK в репозиторий не входят, а `cmd/rocket/rocket_windows_amd64.syso` (результат `windres`) входит и должен пересоздаваться при смене иконки или манифеста.
