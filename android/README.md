# Rocket Android

Kotlin + platform Android APIs only. minSdk 34, target/compileSdk 36. No Compose, AndroidX, coroutines, storage permission, account, TLS or authentication. **Use only on a trusted local network.** The Go daemon listens on IPv4 TCP 42070 and answers UDP 42069 by default; Windows Firewall may require private-network rules (see `../README.md`).

## Language and refresh rate

The default UI is English; Russian device language automatically selects Russian. On Android 13+, Settings → Apps → Rocket → Language offers English and Russian (generated locale config). No in-app language picker or runtime locale dependency is needed.

The rocket scene redraws on display vsync only while something moves (slider drag, flight, results reveal) and the window is visible/focused. It asks the platform for a high View frame rate and prefers a same-resolution 120 Hz window mode when available (otherwise the fastest supported native mode), then restores the prior window preference and default View rate. The OS can override the request for power, thermals or other windows; onDraw timings are **not** proof of presented frames. `RocketRefresh` in debug logcat reports current display mode and onDraw callback spacing. The API 36 emulator tested here advertises only a 60 Hz mode; a physical 120 Hz display is needed to validate 120 Hz output.

## Build / use

Install Android SDK 36 + build tools, set `ANDROID_HOME` or put `sdk.dir=Z:/SDK` in `local.properties`, then run `gradlew.bat :app:assembleDebug --offline` with Gradle 8.13. APK: `app/build/outputs/apk/debug/app-debug.apk`.

**One screen.** The rocket, a **Choose files** button and a gear (Share from other apps works too). After choosing, a files chip, a destination line ("To DESKTOP-ABC") and the **Let's go!** slider appear; dragging it right (≥85%) launches, hides all controls and flies the rocket until the PC confirms; then the rocket leaves and a card shows files, size, time and average speed. Choosing or sharing files never starts a transfer. Successful sending clears the selection; after a failure the files stay selected and nothing is retried automatically (earlier files of a batch may already be on the PC). **Cancel** appears quietly during flight; Back also cancels.

**PC selection is automatic.** With no PC chosen, the app broadcasts `ROCKET_DISCOVER_V1` on UDP 42069 and, if exactly one PC answers (`ROCKET_HERE_V1|<nodeID>|<hostname>`, or the older plain reply), verifies it with TCP ping and remembers it. With several PCs it asks once through the destination line. If the chosen PC stops answering (for example a new DHCP address), the app searches again and follows its public ID without asking. The ID is a display/matching label, **not authentication**.

**Settings (gear)** hold the rest: selected PC (Find PC, Enter IPv4 manually), receive folder (system Downloads or any SAF folder), **Check now** (TCP ping with latency and a discovery count), phone name and version. On Windows, `powershell -File tests/run-smoke.ps1` runs a dependency-free discovery parser smoke test.

The adaptive launcher icon (rocket cut from the user's artwork, background `#272733`, plus a monochrome layer) and `res/drawable-nodpi/rocket.png` are generated by `go run ./tools/genassets` from the repository root; do not edit them by hand. The activity is portrait-only and handles configuration changes itself so a running transfer survives them.
While the Activity is resumed with a selected PC and no active operation, Rocket polls that PC about once a second over TCP for offers addressed to this phone. A stable, randomly generated, lowercase 32-hex device ID is kept in private preferences; the advertised phone name is a sanitized `Build.MODEL`. The PC stages files for the phone; **the phone initiates all TCP connections**. Before each poll the selected PC ID is checked by ping when available, so a changed address owner is not used silently. Each nonempty poll hands its open connection to the transfer operation, downloads the complete offer batch using `offer-get`, verifies raw bytes and CRC32C, publishes each local file, then sends `offer-done` for that offer. Failed processing does not acknowledge an offer, so it can be offered again. If publication succeeded but the acknowledgement was lost, a repeat can create a renamed local duplicate; this is not an exactly-once protocol. Transient poll connection errors are silent. Leaving the screen stops polling and cancels active transfers; there is no service or background polling. If no PC is selected, the app offers discovery/manual selection instead of silently choosing one.

Uploads use ACTION_OPEN_DOCUMENT / share URI streams; the provider **must report a known size** (up to 1 TiB). PUT and offered downloads use one TCP stream per batch. A cancelled or failed transfer closes the socket. Downloads go to system Downloads via `MediaStore.Downloads` with `IS_PENDING=1` until all bytes, CRC32C and stream close succeed; failed entries are deleted. Folder picks use ACTION_OPEN_DOCUMENT_TREE and a persisted grant; they write a `.rocket-*.part` document and rename only after checksum/close, deleting on failure. The provider must permit listing, creating, renaming and deleting documents. No broad filesystem permission is used; Android's picker may prohibit choosing the system Download root as a tree, but the default MediaStore destination supports it.

Filename collision checks are best effort in MediaStore/SAF (providers can hide other apps' files or race). SAF rename **is not guaranteed atomic or no-replace**; some providers can rename differently or fail. MediaStore may also choose a different display name. Downloads do not preserve server mtime. Power loss during a transfer may leave a provider-specific partial SAF document; cancellation after a server ACK/publication can still result in a completed remote file. CRC32C detects accidental corruption but provides no security. Network transfers have a 3-second connect timeout and a 1-hour read timeout during file transfer; the Go server also imposes a 1-hour absolute transfer deadline. The screen stays on during transfers. Progress updates are throttled to about 100 ms and use `SystemClock.elapsedRealtimeNanos()`: PUT counts bytes accepted by the socket's buffered output stream (not confirmed receipt), offered downloads count bytes written to the local target; final success requires the PUT ACK or download checksum, publication and offer acknowledgement. Average speed includes setup and confirmation. TCP offer exchange and physical phone Wi-Fi throughput have not been tested here.
